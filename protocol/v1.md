# Device link v1

The MVP uses request/response HTTP over loopback or a WireGuard-encrypted Tailscale IPv4 path. Each endpoint has one Ed25519 identity. The operator cross-pins public keys before network use. An unpaired peer cannot enroll itself over HTTP. Compromise of the controller key grants all locally approved capabilities. For every agent home and every independently connected accessory, the device operator assigns one full AMP address and pins its exclusive controller key. The bridge reads this policy on every request and rejects key-only legacy assignments. The signed registration carries assignedAgent, which determines the AMP event recipient. Each agent needs an isolated signer; a key shared by multiple agent processes can be used by all of them. The MVP supports one controller per device and one device per controller state directory.

## Exclusive ownership and transfer

Each endpoint has zero or one assigned agent. All capabilities and accessories exposed through that endpoint inherit its assignment. An accessory with its own bridge has its own single assignment. The operator may transfer an endpoint locally by replacing the full AMP address and key together. Transfer replaces the previous grant atomically and camera permission defaults to off. The previous signer cannot start a new operation. While a previous capture drains, requests from the new owner receive HTTP 409 and may retry with a fresh challenge. The bridge rechecks the grant before releasing captured data.

## Encoding

A wire packet is JSON with two strings, `body` and `signature`. Encode each with unpadded base64url. The body decodes to UTF-8 JSON. Sign the UTF-8 bytes of `ai-maestro-device/1`, one NUL byte, then the exact decoded body bytes using Ed25519. Verify the received bytes before parsing JSON. Public keys use the unpadded base64url encoding of the raw 32-byte Ed25519 public key. No key supplied inside a network message participates in trust decisions.

## Exchange

1. Controller obtains `{"challenge":"…"}` from `GET /v1/challenge`. A challenge is 24 random bytes represented as 48 lowercase hex characters. It expires after 30 seconds. At most 512 are outstanding.
2. Controller creates its own independent 24-byte random hex `id`. It signs `{type:"discover",id,challenge,to:deviceKey}` or `{type:"invoke",id,challenge,to:deviceKey,capability}` and posts the packet to `/v1/request`. There are no invocation parameters in v1.
3. Device verifies the current controller pin, target and challenge. It consumes the challenge before dispatch. A retry with the same challenge fails, including after restart. A fresh request is a new operation. After an ambiguous network failure, the caller must decide whether to initiate a new capture.
4. Device signs a response with the same id and challenge and `to:controllerKey`. Discovery returns `{type:"register",version:1,assignedAgent:"agent@host",capabilities:[...],streams:[]}` plus these correlation fields. Registration is solicited by the controller and refreshed on demand. The controller verifies the pinned device key and correlation fields.
5. Invocation returns `{type:"result",ok:true,value:...}` or `{type:"result",ok:false,error:...}`. Signed errors are `denied` or `hardware_unavailable`. Invalid authentication, expired challenges, and malformed packets are rejected with HTTP 403. Unsupported routes return 404, oversized requests 413 and a full challenge pool 429.

| Capability | Local grant | Successful value |
| --- | --- | --- |
| device.health | Pair controller | `{status:"ok",platform:"linux"}` |
| camera.snapshot | Pair controller with camera access; readable /dev/video0 and ffmpeg | `{mime:"image/jpeg",data:"<standard base64>"}` |

Discovery describes currently available handlers. Hardware can fail after discovery. The device serializes camera captures, imposes an eight-second capture timeout, and caps JPEG data at 1 MiB. The wire request limit is 800,000 bytes, including bounded speaker PCM uploads. Replies have a 2 MiB client limit. Unknown capability names and invocation arguments are denied. The device exposes no shell, arbitrary file, URL, executable, or path arguments.

## Events and streams

The controller can emit a user-triggered `device.registered` event only to the assigned AMP agent after verified discovery. Payload fields are version, key, capabilities and observedRequest (the discovery request id). The AMP sender attests to its observation. There is no device-initiated subscription in this HTTP transport. The optional controller monitor refreshes registration and signed health and emits AMP state notices.

The initial profile advertises `streams: []`. Bridges implementing the media extension advertise `video` and/or `microphone` only when locally permitted and available. Speaker consent is separately advertised in `permissions`. Clients discover optional features before use.

### Signed activity updates for displays

A bridge with a display advertises the optional register field `events:["activity"]`. The publisher uses a fresh challenge and posts a signed body with exactly `type:"activity"`, `id`, `challenge`, `to`, `assignedAgent` (full AMP address) and `state` (working, waiting, idle or unknown). The assigned signer and owner must both match the local grant. A successful response is a correlated signed `activity.ack`. Only the state is forwarded; session logs, text and arbitrary markup are excluded. Observation order follows the order in which the bridge issued each challenge. A superseded event receives HTTP 409. Emit a fresh observation about every three seconds; after 15 seconds without an update the reference display reports disconnected.

Displayed state and the most recent successful camera snapshot are volatile and scoped to the current assignment. The local-only screen reads them independently of the signed device transport. A revision change clears both. A signed camera invocation produces exactly one snapshot, mirrored into the PiP for up to a minute while the local camera grant remains active. The screen itself never invokes hardware.


### Media extension

Registration includes mediaFormats for each permitted stream (mime and maxBytes). The v1 profile supports JPEG and mono 16 kHz s16le PCM. A signed request uses type media, kind video or microphone, integer seconds from 1 to 60, and format matching the advertised MIME string. An unsupported format receives HTTP 400; omission selects the fixed v1 default. The usual id, challenge and to fields are required. Only the current assigned signer can open it. A successful response is application/x-ndjson. Every line is an independently signed packet containing the correlated id, challenge, to, kind and a sequence starting at zero.

media.frame carries standard base64 data. Video frames are JPEG, at most 512 KiB, scaled to 640 pixels wide and emitted at 5 fps by the Linux adapter. Microphone chunks are 3,200 bytes of signed 16-bit little-endian mono PCM at 16 kHz. media.end carries a reason (completed, stopped, revoked, or hardware_unavailable). EOF without a signed completed terminal event is an interrupted operation. The sender closes consumers whose outgoing backlog exceeds 1 MB. The receiver bounds each signed packet to 1 MB and checks signature, sequence and session correlation.

A signed speaker request carries at most 320,000 PCM bytes as standard base64 (the same 16 kHz mono format), and receives a signed result after playback. Local consent is independent for video, microphone and speaker. Only one session of each type runs at a time. Video sessions and camera snapshots exclude one another. Disconnect kills capture/playback. The Linux manager checks current grant identity and revision at every frame and at least every 100 ms. Transfer or local consent changes terminate sessions. Local stop revokes all live-media grants.

### Locally approved operator changes

A signed proposal request carries requestId (48 random hex characters) and change. Supported change shapes are action transfer with a new full agent address and public key, action camera with a boolean enabled, or action revoke. The device presents the request locally for five minutes. Until local approval, the existing assignment remains authoritative. Reusing a request ID with another payload fails. A signed proposal.ack reports awaiting_local_approval, confirmed or rejected.

The latest completed receipt remains queryable for 24 hours by the former signer for that exact request. This grants receipt access only. All hardware and discovery requests require the current owner. Transfers reset media permissions and require the new agent's own key. The controller monitor forwards verified receipts to Maestro so an operator sees confirmation instead of treating queueing as success.
