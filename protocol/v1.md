# Device link v1

The MVP uses request/response HTTP over loopback or a WireGuard-encrypted Tailscale IPv4 path. Each endpoint has one Ed25519 identity. The operator cross-pins public keys before network use. An unpaired peer cannot enroll itself over HTTP. Compromise of the controller key grants all locally approved capabilities. The MVP supports one controller per device and one device per controller state directory.

## Encoding

A wire packet is JSON with two strings, `body` and `signature`. Encode each with unpadded base64url. The body decodes to UTF-8 JSON. Sign the UTF-8 bytes of `ai-maestro-device/1`, one NUL byte, then the exact decoded body bytes using Ed25519. Verify the received bytes before parsing JSON. Public keys use the unpadded base64url encoding of the raw 32-byte Ed25519 public key. No key supplied inside a network message participates in trust decisions.

## Exchange

1. Controller obtains `{"challenge":"…"}` from `GET /v1/challenge`. A challenge is 24 random bytes represented as 48 lowercase hex characters. It expires after 30 seconds. At most 512 are outstanding.
2. Controller creates its own independent 24-byte random hex `id`. It signs `{type:"discover",id,challenge,to:deviceKey}` or `{type:"invoke",id,challenge,to:deviceKey,capability}` and posts the packet to `/v1/request`. There are no invocation parameters in v1.
3. Device verifies the current controller pin, target and challenge. It consumes the challenge before dispatch. A retry with the same challenge fails, including after restart. A fresh request is a new operation. After an ambiguous network failure, the caller must decide whether to initiate a new capture.
4. Device signs a response with the same id and challenge and `to:controllerKey`. Discovery returns `{type:"register",version:1,capabilities:[...],streams:[]}` plus these correlation fields. Registration is solicited by the controller and refreshed on demand. The controller verifies the pinned device key and correlation fields.
5. Invocation returns `{type:"result",ok:true,value:...}` or `{type:"result",ok:false,error:...}`. Signed errors are `denied` or `hardware_unavailable`. Invalid authentication, expired challenges, and malformed packets are rejected with HTTP 403. Unsupported routes return 404, oversized requests 413 and a full challenge pool 429.

| Capability | Local grant | Successful value |
| --- | --- | --- |
| device.health | Pair controller | `{status:"ok",platform:"linux"}` |
| camera.snapshot | Pair controller with camera access; readable /dev/video0 and ffmpeg | `{mime:"image/jpeg",data:"<standard base64>"}` |

Discovery describes currently available handlers. Hardware can fail after discovery. The device serializes camera captures, imposes an eight-second capture timeout, and caps JPEG data at 1 MiB. The wire request limit is 8 KiB. Replies have a 2 MiB client limit. Unknown capability names and invocation arguments are denied. The device exposes no shell, arbitrary file, URL, executable, or path arguments.

## Events and streams

The controller can emit a user-triggered `device.registered` event to an AMP recipient after verified discovery. Payload fields are version, key, capabilities and observedRequest (the discovery request id). The AMP sender attests to its observation. There is no background subscription in v1.

`streams: []` is mandatory for this profile. Reserved future capabilities are `microphone.stream` and `speaker.play`. A media profile needs separate local consent, codec negotiation, sequence numbers, backpressure, size and duration limits, and stop-on-disconnect behavior before a bridge may advertise it. Real-time audio and video calls remain outside this MVP.
