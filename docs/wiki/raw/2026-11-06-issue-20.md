## Summary

The agent display page (served by the device bridge on `127.0.0.1:23111`, shown in a Chromium kiosk) grew to about 3.2 GB of memory after roughly 6.5 hours. The laptop ran out of free RAM and Chromium showed "Page unresponsive".

## Observed (protocol commit `ffdda4d`, then `c07c0e9`)

- Device: Omarchy (Arch Linux) laptop, 7.6 GB RAM, Chromium kiosk with its own profile (`--user-data-dir=~/.local/share/agent-display-chromium`), page `http://127.0.0.1:23111`.
- Before restart: the page's renderer process held 42.7% of memory (about 3.2 GB) after 6 h 39 min. Free RAM was 210 MB. Load average was 5.9.
- The bridge and the display server were healthy: `/state` answered HTTP 200 in 17 ms. Only the page was stuck.
- After restarting the kiosk: the renderer used about 2% of memory and free RAM was 3.8 GB.
- During that time the agent display showed camera frames from `camera.snapshot`, plus a mic/speaker/camera indicator, and the watch service on the controller published agent state regularly.

## Not confirmed

I did not profile the page, so I do not know which part leaks. Likely candidates: camera frames kept as data URLs or Blob URLs that are never revoked, an array of state or event history that only grows, a polling or SSE loop that adds listeners or DOM nodes on every tick, or a CSS animation of the orb that is re-created.

## Expected

The page runs for days without memory growth, because it is a permanent kiosk.

## Suggested fix

1. Reproduce: open the page in Chromium with DevTools and take heap snapshots (or the Memory tab timeline) over 30 to 60 minutes of idle and a few snapshots.
2. Revoke object URLs and keep only the latest camera frame.
3. Bound any history or log kept in the page.
4. Optional safety net: `location.reload()` once per day when the page is idle, or reload on a heap limit (`performance.memory`).

## Workaround

Restart the kiosk: stop Chromium and run `~/.local/bin/agent-display-kiosk`.
